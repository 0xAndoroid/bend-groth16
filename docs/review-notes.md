# Review notes

Pre-release self-review of the Bend 2 prover, judged against gnark-crypto v0.21.0 / gnark v0.16.3 and arkworks 0.5.0. Sections: A Bend 2 usage, B Algorithms, C Why GPU < CPU.
## A. Bend 2 usage

Scope: `bend2/src/*.bend`, `bend2/prove.bend`, `bend2/gen/*.py`, against Bend **2.0.5** (`~/.bend/current/bend2/{comp,bend}.ts`, `~/.bend/current/guide/GUIDE.md`) and upstream `bendlang/bend` at 2.0.13 (`bench/runtime/{bfs,tree-matmul}/main.bend` as the author's own style reference). Cites are `file:line` at this commit.

**Model.** Bend 2 is not HVM: there are no interaction nets, no `fold`/`bend` keywords, no dup nodes and no interaction counter (none of those words occur in `GUIDE.md`; the scheduler paragraph is `GUIDE.md:154-157`; the runtime binary only takes `--threads`, `--gpu`, `--gpu-build`, `comp.ts:5863-5880`). Each def compiles to a C state-machine segment, parallel lets fork tasks onto a fixed-placement fork-join scheduler, values are 64-bit words in one arena, and only `+`-shared *constructor* values are refcounted (`rfc_seal` is a no-op for anything that is not a `TAG_CTR`, `comp.ts:3810-3815`). The questions below are answered against that model, not the HVM one.

### How the field code actually compiles (measured, not assumed)

- `bend2/bench/field_mul.bend -o field_mul.c`: `Fr.mul` becomes `spin_4(Env e, Term* o, u32 r0 … u32 r31)` — both 16-limb records arrive as 32 flat `u32` parameters, every `+vN` SSA let is a `u32` C local, the result leaves through `o[0..15]`; zero `heap_alloc`/`e.mem[]` traffic inside the multiplier. `G1` (48 words) is likewise passed flat (`spin_18` with 48 `u32` params in `g1_add.c`). So the "dup nodes → memory traffic" worry does not apply: `+` on `U32`/flat records is a register copy, and the `+` marks on single-use `vN` lets are free.
- Single-thread throughput, M4: `field_mul` N=20 `--threads 1` = 116 ms on an idle host → **9.0 M mul/s** (138–152 ms, 7.0–7.6 M, with other jobs running), including the hash-generated operands. Handwritten C, same 16×16-bit CIOS fully unrolled, same operands, `clang -O3`, measured on the loaded host: **10.5 M mul/s**. Conventional 4×64-bit CIOS with `__int128`: **55.5 M mul/s**. Bend's codegen is within 1.2–1.4× of equivalent C; the missing ~5× is the 16-bit-limb representation that U32-only arithmetic forces (no mul-hi, no carry). The C baselines (60 lines of textbook CIOS) are not committed.
- Thread scaling of the pure fork tree, N=24 FD=14: 1 thread 1855–2149 ms → 10 threads 454–663 ms = **3.2–4.1×** on 4P+6E cores. With no work stealing (`GUIDE.md:155-157`; `task_deal`, `comp.ts:4212-4236`) a leaf lands on a core once; 2^14 equal leaves spread round-robin means the wall clock is the E-core's share, so ~4× is the ceiling for this shape on this chip regardless of what the leaves compute. NTT stages show the same ~4× (`bend2/bench/ntt_results.md:35`), the prover 2.1× at K=14 (`bend2/bench/prover_results.md:120`).

### Review questions

1. **fold/bend vs manual recursion.** Not applicable in Bend 2: the loop forms *are* `Nat` count-down tail recursion and `Nat`-depth fork trees (`GUIDE.md:89-126,130-160`). Every hot loop here is one of those (`Msm.g1.pts:133`, `Ntt.bfc:130`, `Ntt.bfr.blk:193`, `Sc.canon:213`, `Ev.ents:125`); non-tail recursion exists only in cold helpers (`Groth.clog2.go:71`, depth 31; `Groth.word.bytes:82`, depth 4) and along fork trees, where it belongs. Nothing to hand back to a library.
2. **Affine/dup discipline.** Field elements and points are flat records: the emitted C passes `Fr` as 32 and `G1` as 48 `u32` parameters and never boxes them, so `+` costs a word copy, not a refcount cell. The only wasted copies are the re-materialised `G1{…}` arguments to the `*.fin` selectors (finding 5, ~1 %). Arrays are used as intended — indexed in place through `a[i] <- v` / staged `a[i]` reads, no `Array.clone` anywhere, ownership threaded through the state records — except at fork points, where the `ANode` split/join copies (finding 3, ~3 %).
3. **U32 packing.** 16 × 16-bit limbs in `U32` is the correct choice under U32-only arithmetic: one CIOS cell `t + a·b + c ≤ 2^32 − 1` is exact, so there is no carry bookkeeping beyond `and`/`shrn` (`fr.bend:272-274`: 3 ops per cell, ~800 ops per mul). 30/31-bit limbs are impossible without a 64-bit product; `Nat` (48-bit) limbs would need a hardware `divmod` per cell and abort on overflow (`docs/bend2-idioms.md:57`). Measured cost of the representation vs 4×64-bit C: ~5×; Bend's own overhead on top: 1.2–1.4×.
4. **Parallel structure.** The shapes are right — balanced `Nat`-depth trees with equal leaves (`Msm.g1.tree:165`, `Ntt.early/late:161,229`, `Ntt.point:359`), one `!` per phase (`prove.bend:28,38,48`) — and the scaling ceiling is the scheduler: fixed placement across 4P+6E cores caps a perfectly balanced tree at ~4× (`field_mul` 3.2–4.1×, NTT ~4×), and the MSM's two serial tails (`Msm.g1.join:148`, a sequential pass over wt·2^c buckets at each of the fd join levels; `Msm.g1.red:182`, 2^c sequential adds per window) plus ~3 % split/join copies pull the prover to 2.1× on 10 threads (`bend2/bench/prover_results.md:120`). No interaction counts exist to report; the measurements above are the substitute.
5. **Would the author wince?** At two things, both fixed here (findings 1–2). Generation is the right call: Bend 2 has no metaprogramming, no limb loops without arrays, and a 2.5k-line straight-line def compiles in seconds (`docs/bend2-idioms.md:104`); the generators are committed under `bend2/gen/` and now reproduce every generated file byte-for-byte (`uv run python bend2/gen/gen_{field,curve,msm,ntt}.py` → clean `git status`). Style otherwise matches upstream's own benchmarks (stage defs, `Bool`-to-def dispatch, `+` binders, state records). `!` is used correctly (one coarse call per phase, no IO underneath). Remaining wince candidates are the ones the language forces (findings 3, 4, 6, 8) and should be presented as such, with the numbers.

Where the two reviews disagree — window size. One says c = 15-16 by-window Pippenger needs 1.8-1.9× fewer Fq multiplications than our c = 8; the other says raising c alone regresses because of the bucket-set joins. Both are right about different designs. The 1.9× is real but belongs to by-window parallelism, where every task reads the whole point array: with single-owner arrays that is W clones of points + scalars (17 × 48 MiB = 0.86 GB at 2^18 for c = 15). With our fork-by-point-range topology the join costs (2^fd − 1)·W·2^c Jacobian adds, which grows as 2^c: at c = 15 it is 127 × 17 × 32 768 ≈ 71 M adds against 8.4 M bucket adds, so c = 8 is close to the cost-model minimum for this topology (measured: c = 8 / fd = 7 gave 2.6× over c = 12 / fd = 4 on the K=18 prover, 10 threads). Signed digits (#3) are the only window change that pays without changing the topology.

Deliberate trade-offs, kept for publication:

1. **MSM shape: c = 8, 32 windows, fork by point range, element-wise bucket join** instead of by-window Pippenger with signed c = 15-16. Cost at K=18: `msm_a` ≈109 M Fq-mul vs ≈58 M (1.9×), `msm_h` 201 M vs 109 M, and at 2^20 (c = 10) 354 M vs 202 M (1.75×). Reason: by-window parallelism needs shared read-only access to the inputs; Bend 2 arrays are single-owner, so each window task would hold its own copy (0.86 GB at 2^18, ≈3.4 GB at 2^20) or the design needs another read-only representation. The point-range topology copies nothing but the bucket sets, and its join is 6-13 % of the bucket adds at c = 8.
2. **Field multiplication: 16×16-bit CIOS with per-cell normalisation, 2801 U32 ops per mul,** instead of ≈1860 with 20×13-bit limbs and lazy carries (−34 % ops, estimated 1.3-1.6× on the whole prover). Reason: Bend 2 has U32 only (wrapping mul, no mul-hi, no U64), so the 16-bit split is the largest one whose CIOS cells cannot overflow ((2^16 − 1)^2 + 2(2^16 − 1) = 2^32 − 1); a 13-bit lazy-carry kernel changes R, the reduction bounds and every generated field routine, and its gain is an operation count that `bench/field_mul.bend` has not yet confirmed. Squaring (#5) and lazy add/sub (#6) only pay on top of it.

Fixed before publishing (M4 Mac mini, 10 threads unless noted; medians of 3 runs at K=10/14, one run at K=18):

- MSM: test the bucket for ∞ before `add_mixed` (`Msm.*.badd.s`; G1 and G2, generated) — one wasted mixed add per bucket per leaf removed. Measured: K=14 total 5.49 → 4.28 s (−22 %; 1 thread 11.66 → 8.74 s, −25 %), K=10 0.65 → 0.49 s, K=18 MSM phases −4…−8 % (31.4 → 30.1 s total).
- QAP: one fused scale pass (n^−1 · g^j) per `qap_h` pipeline instead of two — 6D Fr-mul and three array passes.
- R1CS evaluation: coefficient 1 skips the Fr multiplication (all 786 432 K=18 coefficients).
- Scalars: convert `z` to canonical form once and copy its suffix, instead of converting `z` and `zl` separately.
- The three QAP/evals fixes together: `qap` K=14 88 → 79 ms (1 thread 402 → 356 ms), K=18 1336 → 1310 ms; `evals` K=14 10 → 4 ms, K=18 163 → 54 ms. Small against a 31 s prover, but they were the cheapest items on both lists.

Open items (for a Bend issue):

- Signed-digit recoding, c = 9 with 2^8 buckets: 32 → 29 windows, −9.4 % bucket adds and join, same memory (#3).
- 13-bit lazy-carry Montgomery multiplication in `gen_field.py`, measured with `bench/field_mul.bend` first; then dedicated squaring and lazy add/sub (#4, #5, #6).
- By-window MSM parallelism needs a zero-copy read-only array view (or persistent owned chunks) to reach gnark's c = 15-16 (#1); the same primitive would remove the MSM split/restore copies (672 MiB at 2^18) and the QAP boundary copies (1.5 GiB at D = 2^19).
- Skip unity twiddles (stage 0) and cache per-level twiddle tables (#10, #11); in-place NTT stages (#12).
- Prune empty padded MSM leaves (#13); Horner recombination and a small-n window table (#14, #15).
- Fold Z^−1 into the final coset iNTT's scale (≈D Fr-mul); a reduction-only Montgomery exit kernel (528 → 272 products per conversion).

## C. Why GPU < CPU

**Verdict.** The `!` path loses because our MSM/NTT give the device a few dozen–few thousand long *sequential*, memory-walking tasks split by host-synchronised barriers, while one Bend device lane is
~15× slower than one M4 core on field arithmetic and ≥100× slower on array traffic. Not the backend's fault: the same binary runs an embarrassingly parallel `Fr.mul` batch **≈5× faster than 10 cores**
on the mini (≈0.7–1 G mul/s net of the first-call cost) and 110× faster than 48 threads on the RTX 5090.

**Runtime facts** (`~/.bend/current/bend2/comp.ts`; not HVM, no interaction nets). One C file is host program and Metal/CUDA kernel (`#embed __FILE__`, NVRTC / `newLibraryWithSource:`); a def is a
segment of a flat state machine. A `!` marks one task (`fid_bangs`); `cube_run` (`comp.ts:5030,5121`) then loops **rounds**: one command buffer of ≤4 `bend_dev` launches — grow (1 group, ≤`CUBE_T`=128
turns), grow (128 groups), work (each lane drains its own ring until empty), pack — then `waitUntilCompleted` / `cuCtxSynchronize`. 2^`CUBE_LOG`=128 groups × 128 threads = **16384 lanes** (CUDA clamps
to the same); a task is pushed to one ring and never moves (no stealing); work whose continuation is not picked up inside the pass (an NTT stage boundary, measured below) costs another round. Memory
is the one host arena (`newBufferWithBytesNoCopy` / `cuMemAllocManaged`; no wholesale copies); cells are 64-bit terms addressed per lane from wherever the allocator put them — nothing coalesces them.
The "~55 ms per `!`" folklore is a **per-process first-call cost** (50–60 ms: first vs second `!` of a process, `gpu_lane`); a steady-state `!` costs a few ms, an extra round ≈1 ms at small data.

**Model.** *s* = lane slowdown (≈15 ALU / ≥100 memory on Metal; ≈7 ALU on CUDA), *P* = CPU speedup over one thread (4.6 mini, 17.8 box), *L* = tasks busy along the critical path. The device wins iff
*L*/*s* > *P* **and** the tasks are SIMD-uniform: a lane is an independent `switch`-driven state machine and 32 lanes step in lockstep, so absent or divergent neighbours idle a SIMD group (measured:
16 leaves run at full lane speed, 128 at ¼ each; throughput saturates past ~2^12 leaves at ≈0.7–1 G mul/s ≈ 80–110 core-equivalents). **Break-even: ≈70–90 busy uniform ALU lanes on the mini (≈500 for
memory-walking code), ≈125 / ~1000 on the box.**
- **MSM v2** (`bend2/src/msm.bend`): 2^fd ≤ 128 leaves (32 at 2^14, 2 at 2^10), each a *sequential* Pippenger over W windows with a private 2^c-bucket array (8 MiB at c=10); every bucket add moves 48+48
  bucket words + a 32-word point at random offsets (memory-shaped). The join then adds (2^fd−1)·W·2^c buckets in a tree whose top level is **one lane**. 2^14/fd 5: critical path ≈ 16k leaf + 5×8k join
  = 56k adds × 39 µs per lane add (`g1_add` FD 0: 646 ms / 2^14) = 2.2 s ALU floor; 6.4 s measured, the rest is bucket latency + the ∞-fill/read of 32×256×64 words per leaf. The model only brackets
  this: with *s* = 15 (ALU) *L*/*s* = 2 ≈ *P* predicts parity, with *s* ≈ 100 (bucket traffic) it predicts 1362 ms × 100 / 32 ≈ 4.3 s + join ≈ 7–10× (9.4–9.8× measured); 2^10 (L=2) is ≫ slower either
  way. The box 2^20 fd 9 run (1.8×) sits between the same two bounds. `nvidia-smi` 100 % = one resident kernel, not occupancy. The winning `field_mul`/`g1_add` benches had register inputs, no arrays,
  2^14–2^16 identical leaves, one round.
- **NTT** (`bend2/src/ntt.bend`, Stockham chunk tree): every radix-2 stage's join returns to the host ⇒ **rounds = log2 n + 2** (measured, CPU and GPU). Per round at 2^18: 2^17 butterflies over ≥8192 lanes
  = a few tens of `Fr.mul` per lane ≈ 0.05 ms of ALU, yet 44 ms measured: the stage streams 2×16 MB of cells (+ a freshly allocated output chunk per task) through per-lane 8-byte accesses ⇒ ≈0.8 GB/s
  effective vs ~100 GB/s peak; 10 CPU threads move the same 32 MB in 6 ms. qap_h loses least (2.2–2.5×): 3 pipelines overlap.

**What would flip it** (expected effect):
1. *Program:* bucket-sorted MSM — parallel radix sort of (digit, point) per window (itself ≥2^12 uniform leaves), one lane per bucket summing a contiguous run, tree reduction ⇒ L ≈ W·2^c ≈ 26k uniform
   tasks, no private 8 MiB arrays, no serial join. Needs a shared read-only point array; in 2.0.5 arrays are single-owner and `ANode` splits copy ([#804](https://github.com/bendlang/bend/issues/804))
   ⇒ a 128 MB clone per window or a segmented owned layout. Expected MSM 2^20: 106 s (v1 Metal) → 1–3 s, 17 s → 0.2–0.5 s (CUDA): 5090 ~20× over 48 threads, mini ~5× over 10.
2. *Program:* NTT with ≥4 radix-2 stages fused per round (lane owns a 2^k chunk, k stages in registers) and a lane-major (SoA) layout so neighbouring lanes hit neighbouring words: rounds 20 → 5,
   coalescing penalty ~10× → fft 2^20 3.4 s → ≈0.3 s (CPU×10 0.53 s).
3. *Runtime:* keep join trees on the device until the root finishes (removes stage rounds with no program change); a borrowed/shared immutable `Array`; `U32.mulhi` or a 64-bit product (8×32-bit limbs
   ⇒ ~3× fewer cells per mul); ring work stealing.
4. Without 1–2 the phase-wise `BENDG_GPU=1` prover cannot win at any K: its five MSMs offer ≤128 (mini) / ≤512 (box) busy lanes.
